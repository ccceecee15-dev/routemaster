Important Architectural Correction

After further review with the client, we need to adjust how the Route Master is represented.

The current implementation unintentionally implies that a Store belongs to a Category or Merchandise Area.

This is not the business model.

A store can carry products from many Categories and many Merchandise Areas.

Instead, Category and Merchandise Area describe the merchandise travelling on the route, not the Store.

The Route Master should therefore be thought of as:

Warehouse + Store + Merchandise Classification → Lead Time

where Merchandise Classification may be maintained at different levels of specificity.

Merchandise Classification

Reorganise the UI so Category and Merchandise Area are visually grouped together as part of a single Merchandise Classification section.

Within the table, keep separate columns but place them next to one another.

Example:

Warehouse	Store	Category	Merchandise Area	Lead Time (Weeks)

This makes it clear these fields describe the merchandise, not the Store.

Introduce Default vs Exception Rules

The client explained that lead times are generally maintained at the Category level.

Only where necessary should a more specific Merchandise Area rule be created.

This means Route Master contains both:

Default rules
Exception rules
Example

Default Rule

Warehouse	Store	Category	Merchandise Area	Lead Time
RDC Vegas	S101	Apparel	All Merchandise Areas	2 Weeks

Exception

Warehouse	Store	Category	Merchandise Area	Lead Time
RDC Vegas	S101	Apparel	Womens Knitwear	3 Weeks

The second row overrides the default only for Womens Knitwear.

No business logic needs to be implemented.

This is purely represented through mock data.

Important

Do not implement inheritance logic or override calculations.

The goal is simply to make the Route Master accurately represent the client's business process:

Stores can carry many Categories and Merchandise Areas.
Category defines the standard routing rule.
Merchandise Area defines exceptions when required.
Multiple Route Master rows for the same Warehouse and Store are expected because they represent different merchandise classifications rather than duplicate routes.

Continue using realistic mock data and frontend-only behaviour. The focus is a polished, intuitive UI that accurately reflects the intended business model while remaining fully consistent with the existing MerchX application.
